## Decisions (What If mandate: adjust with a justification, report here + handover)
1. **Worst-sector target.** 2.0 ms was the orchestrator's headroom split for RG-169's surface base, not a streaming limit (`BudgetMs` 3 is per frame on the NightRacer main thread). Decision: What If sector builds are pure CPU, Unity-free library work and run on a **background thread**; the per-frame main-thread cost is the mesh upload (measured later in Unity). The protocol for RG-169 is therefore: sweep median <= 2.0 ms and P95 <= 3.0 ms per sector (throughput), worst sector reported against 3.5 ms. Throughput check: at 108 km/h a new row of ~4-5 level-15 sectors (~300 m) is needed every ~10 s — orders of magnitude below one background thread's capacity at 3 ms/sector.
2. **Carried into RG-169:** worker's option (B) — evaluate the base once per point and pass it into the carve (additive `HeightBatch` overload with precomputed base; the surface base is ~1 ms per 65 x 65, so a second evaluation inside `Natural` would be unaffordable); option (C) = decision 1.
3. **Experiment wall time 381 s > 300 s:** RG-169 runs the sweep in ecost process 1 only (worker's proposal); the worst-sector protocol rows keep the 3-process median.
4. **`run-experiment.ps1` throws while the lock is held:** RG-169 makes it (and `run-surface.ps1`) wait like `scripts/test.ps1`.
5. Region world build times in the worker CSV are 10-40 % slower than main (e.g. face-centre sequential 12.4 -> 13.9 s). `Generator` does not call the new batch path; the worker ran while RG-168/RG-171 compiled and measured. See the rerun above for the quiet-machine comparison.
